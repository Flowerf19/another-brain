# 0.13.0 dev — Pi tool prefix and pip installation

## Summary

Keep Another Brain's MCP wire-level tool contract unchanged:
`brain_remember`, `brain_search`, `brain_recent`, `brain_get`,
`brain_reinforce`, `brain_forget`, `brain_health`, and `brain_audit`.

Change only the Pi adapter registration generated by `another-brain connect pi`.
Pi currently uses its default `toolPrefix: "server"`, so the configured server
`another-brain` turns `brain_health` into `another_brain_brain_health`. The Pi
entry should set `toolPrefix: "none"`, making the exposed Pi tool name exactly
`brain_health` while leaving every other harness and the MCP server unchanged.

Make ordinary pip installation a first-class supported path. Hatchling already
provides the PEP 517 build backend that pip uses; the actual gap is that user
docs, developer metadata, CI, and actionable install messages currently make
uv look mandatory. `uv.lock` remains a maintainer/development lockfile, not a
runtime requirement for pip users.

## Naming decision and examples

The public names do not change in `another_brain/mcp/tools.py`:

```text
MCP wire tool: brain_health
```

Before, with Pi's default prefix:

```text
mcpServers.another-brain = {"command": "another-brain"}
Pi tool         = another_brain_brain_health
```

After, for Pi only:

```json
{
  "mcpServers": {
    "another-brain": {
      "command": "another-brain",
      "toolPrefix": "none"
    }
  }
}
```

```text
MCP wire tool:   brain_health
Pi exposed tool: brain_health
```

`another-brain/brain_health` may be used by a host or document as a qualified
`server/tool` display, but it is not passed as the MCP wire tool name. The
`toolPrefix: "none"` setting is Pi-specific and may cause collisions if a user
has multiple MCP servers exposing the same names; document that trade-off.

## Files and ownership

- MCP tool registration stays in `another_brain/mcp/tools.py`; no handler
  names or `tools/list` names are renamed.
- Per-harness configuration ownership stays in the ``harness`` service
  package (``another_brain/services/harness/``): rows live in
  ``harnesses.yaml``, behavior in ``service.py``; do not put ``toolPrefix``
  in the global ``SERVER_ENTRY`` used by all harnesses.
- Pi's generated target remains `~/.config/mcp/mcp.json`, as currently used by
  the connector.
- Packaging metadata is owned by `pyproject.toml`; the lock update belongs in
  `uv.lock`.
- User-facing install/configuration docs: `README.md`, `docs/deployment.md`,
  `docs/mcp-tools.md`, `installer/README.md`, and `CHANGELOG.md`.
- Project guidance affected by install commands:
  `.agents/PROJECT_CONTEXT.md`, `.agents/TESTING_GUIDE.md`, and any stale
  canonical-install statement in `.agents/AGENT_RULES.md`.
- CI changes belong in `.github/workflows/unit-tests.yml`,
  `.github/workflows/wheel-gate.yml`, and the pip gate's integration wrapper.

### pip

- Build/install from the checkout in a fresh environment with standard pip:

  ```bash
  python -m venv .tmp-pip-venv
  .tmp-pip-venv/bin/python -m pip install .
  .tmp-pip-venv/bin/python -m pip show another-brain
  ```

  Use the equivalent `Scripts\\python.exe` path on Windows. Run the installed
  command from a neutral directory and verify `--version`, `--help`, and that
  `another_brain.__file__` is inside the venv, not the checkout.

- Build a wheel using `python -m pip wheel .` and install it into a separate
  clean venv with `python -m pip install`; verify declared runtime dependencies
  resolve without `uv` or `uv.lock`.
- Verify `python -m pip install -e ".[dev]"` provides the test dependencies,
  while `uv sync --locked --extra dev` and the existing uv test commands remain
  green after the lock refresh.
- Run `git diff --check`, focused unit tests, the full suite, the pip gate, the
  existing uv wheel gate, and `scripts/check-clean-tree.sh`.

## Acceptance criteria

1. After `another-brain connect pi`, Pi exposes `brain_health`, not
   `another_brain_brain_health`; the server still receives the wire name
   `brain_health`.
2. Other harnesses retain their existing registration payloads, and no MCP
   `brain_*` tool is renamed or aliased.
3. A clean environment with ordinary pip can install and start the published
   or locally built package without uv, `uv.lock`, Docker, or a source checkout
   on `sys.path`.
4. `pip install -e ".[dev]"` and the uv development workflow use the same
   declared test dependencies without an untested duplicate list.
5. Documentation and doctor guidance show both supported installation paths.

## Assumptions

- The user wants only the Pi presentation shortened; the MCP protocol surface
  remains the stable `brain_*` contract.
- The Pi adapter version in use supports per-server `toolPrefix` and defines
  `"none"` as no server prefix; this is verified in the installed adapter's
  `types.ts` and README before implementation.
- No compatibility alias or source-level tool rename is needed.
- The package version remains unchanged until the normal 0.13.0 release step;
  this plan tracks development work on branch `0.13.0-dev`.
